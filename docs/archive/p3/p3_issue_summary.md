# P3 问题与解决方法汇总

> 历史归档（2026-11-12 整理）：保留当时的实现、证据与待验状态。正文中的“当前”“下一步”、旧构建目录和命令均属于该批记录；日常操作请查[操作指南](../../operations.md)，最新状态请查[当前进度](../../realtime_voice_progress.md)，返回[文档索引](../../README.md)。归档不改变未验收事项。

更新：2026-11-10。依据项目问题记录、当前源码、已有检查日志及用户现场反馈整理。

P3 已实现 ESP32 实时采集、Opus、WebSocket、播放和手动控制，并能实机对话；完整硬件与长时稳定验收仍未结束。已有代码修复不等于现场问题全部消失。下面分别记录现场故障、开发检查修复和待验收的保护措施。

## 1. 录音、服务端与待机

| 问题 | 原因与确认依据 | 已采取的解决方法 | 当前状态 |
| --- | --- | --- | --- |
| 持续录音几秒后断开（P3-001） | 旧 ASR 节拍按“发送完成时间＋音频时长”安排下一块，发送和调度耗时逐块累积，可能填满服务端队列；代码机制及无云模拟已确认，不能据此解释所有现场断线 | 按首包开始时间和累计 PCM 样本计算绝对 deadline，限制迟到后的追赶速度，覆盖尾块、取消和下一轮 | 代码已修复，30 秒离线回归通过；后续网络停顿另行定位 |
| 设备上行任务短暂积压（P3-002） | Opus 和网络发送在同一任务顺序执行；现场有一次约 223–225 ms 发送阻塞，本地队列升至 11 帧。正常整帧平均约 10 ms，尚无持续编码算力不足证据 | 采集编码、发送和整帧耗时、队列及资源水位；汇总日志移到控制任务。单包预算保持 200 ms、可配置对照；Wi-Fi 默认关闭省电 | 已补诊断和对照配置，底层停顿原因仍待定位 |
| 服务端队列短暂满就立即失败（P3-009） | 集中到达的音频突发可使 25 项队列暂满，原逻辑立即抛错；现场出现 queue=25 和接收突发 | 保持 25 项有界队列，暂满最多等待 100 ms；每次入队主动让出调度；监测 worker 失败，取消等待不会迟到插包 | 突发、顺序、慢消费者及取消回归通过；持续积压仍明确失败 |
| 队列为空也报 uplink_backlog | 只看应用队列会漏掉 TCP／其他缓冲中的迟到音频。最新现场本轮到达空档 1406 ms、媒体落后 1341 ms；另一轮空档 2531 ms、落后 2460 ms | 按本轮服务端经过时间与 sample_offset 计算媒体进度，在入队、消费及解码后检查 750 ms 上限；增加本轮接收及最老音频年龄指标 | 保护已实现并在现场触发；音频停顿未解决，网络卡顿只是候选原因之一 |
| 约 90 秒待机后显示服务错误（P3-008） | 原业务空闲策略到期，与协议／上游错误共用 1008 关闭路径；后续配对日志确认过 idle_timeout。部分更早历史轮次缺配对日志，仍不能追认原因 | 默认 idle_timeout_seconds=0 长期待机；有限待机才正常发送 session.closed/idle_timeout，以 1000 关闭。录音、ASR 收尾、回复及播放保护不算待机；正常结束后 r 可建立新会话 | 用户反馈新版待机未再报错；至少 5 分钟及随后录音的正式验收仍待记录。与准备录音交叉时保守报 idle_close_active |
| 风扇背景声录音约 30 秒后 ASR 失败 | 现场 asr_reason=receive_timeout：旧逻辑要求单次 receive 在 30 秒内返回，但持续上传噪声／静音时可能没有中间识别结果，期限与设备自动收尾相撞 | 录音期按成功发送的非空普通音频刷新输入进度；保留一个 receive；有序结束后旧期限不抢先失败；EOF 成功后给最终结果独立预算。握手、发送、真正停滞及缺失 final 仍有超时 | 代码已修复，最新历史完整服务端 183 项及针对性 40 项通过；真实背景声与连续回合仍待完整复验 |
| 没有出现“未识别到语音” | 此提示要求录音正常结束且云端返回真实空 final；此前 ASR／传输先失败就无法完成该流程，背景声也可能被识别成非空文字 | 真正空 final 走 asr.utterance_final 空文本及 response.done/empty_utterance，保留会话；缺 final、云端拒绝、断线等仍报告真实错误 | 空结果路径及同会话下一轮已离线验证；不保证任意风扇声都返回空文字 |
| 未按 s 却自动进入处理／思考 | 当前固件录满 1500 个 20 ms 帧，即约 30 秒，会主动发送 Opus 尾包、audio.stream.end 和 speech.end。P3 没有 VAD，手动录音期间噪声也上传 | 明确此为现有时长保护；P4 再加入 ESP-SR／VADNet、预录和自动端点，将“未检测到讲话”与有效发言分开 | 属 P3 能力边界，P4 待实施；屏幕进入处理状态本身不能证明 LLM 已开始或卡住 |
| 修改后仍运行旧服务，误判修复未生效 | 用户明确确认其中一组 idle_timeout／uplink_backlog 日志来自旧进程 | 修改 Python 后退出旧服务并重启；核对启动入口、profile、版本和本轮身份。仅改服务端时不要求重烧固件 | 该组旧进程记录已排除出新版回归结论，不能据此排除其他新版故障 |

## 2. 固件、显示与诊断

| 问题 | 原因 | 已采取的解决方法 | 当前状态 |
| --- | --- | --- | --- |
| GPIO8 重复占用告警（P3-003） | 扬声器每次 DMA 重建都重新登记 SD 脚，旧 deinit 未解除占用登记 | 分离 SD 引脚与 I2S／DMA 生命周期；重建时保留登记并拉低 SD；完整释放时解除登记；初始化检查所有权 | 100 次静音重建、14 种失败恢复等主机回归通过，实际电平／爆音／停播听感仍待确认；没有证据证明它导致 WS 断线 |
| LCD 完成回调被覆盖（P3-006） | ST7789 初始化、LVGL 接管及 attach 路径重复设置回调 | 统一由 LVGL 注册一次；接管前排空独立绘图 DMA，接管后不混入独立绘图 | 代码及构建通过，上电告警和实际刷新仍待完整验收 |
| 长回答显示不全（P3-007） | 对话仅保存 319 字节，正文没有分页；显示限制与服务端 TTS 文本相互独立 | 改为 8192 字节有界缓冲，最多保存 8191 字节有效 UTF-8；每页三行、每 5 秒自动翻页，串口 [／] 手动翻页后暂停自动 15 秒；增量追加保持当前页，超限提示省略 | 67 项文字／UTF-8 主机检查通过，LCD 实际显示与听感仍待确认；显示容量不会截断 TTS |
| 后续清理错误覆盖第一次故障（P3-004） | 多任务同时失败，Disconnected、发送失败和重建日志混在一起，屏幕提示会被覆盖 | 两端锁定 first_failure，后续仅作 secondary_failure；记录 attempt／epoch／turn／stream、阶段、关闭码及耗时；清理后恢复首个提示 | 已实施，首因与错误传播回归通过，现场已能区分多个故障类别 |
| errno 显示随机值或被误读（P3-005） | ESP WS 组件仅在 TCP 错误类型初始化 socket errno；应用原来对其他类型也读取。另有 SDK poll 超时分支可能保留旧 errno | 应用只在 TCP 错误读取该字段，其他类型记 0（不可用）；分析时区分返回 0 的等待到期与明确 socket 错误 | 应用读取问题已修复并回归；SDK 打印 errno=5 不足以定案为硬件／GPIO故障，未修改 SDK |
| 连接未录音却显示旧帧数（P3-010） | 新连接未重置上轮统计，旧 End 任务也可能迟到覆盖新轮值 | 新 attempt、session.ready 和 turn 重置；更新统计时在锁内核对身份，输出 active_epoch／active_turn／metrics_current；区分连接累计和本轮接收指标 | 生产控制器主机回归通过；连接级最大间隔仍可能包含跨轮等待，不等于本轮录音停顿 |
| server_error／provider_failed 无法区分 ASR 原因 | 上游和协议异常原来分类粗，ASR reader 可能先失败、下一次 feed 才发现 | 增加固定 asr_reason、有效数字上游错误码和 ASR 关闭码；记录队列等待、decode／feed、发送进行中状态、事件循环延迟、接收空档及突发 | 已实施并帮助确认 receive_timeout；只输出固定分类和数字，不打印凭证、音频或厂商正文 |

## 3. 开发检查中补齐的修复与保护

下列项有代码／检查证据，但不能全部称为用户设备上已发生的现场故障。

| 检查项 | 处理方法与验证边界 |
| --- | --- |
| UART0 命令接收缺 RX 驱动初始化 | 安装 UART0 RX 驱动后再读取 r/s/c/n/?；使用 UART0 实际连接，USB Serial/JTAG 能显示日志不代表能接收这些命令 |
| 重连与旧 Start／旧发送任务竞态 | 先禁止采集、失效旧 epoch，再等待发送屏障和接收任务退出；旧项按身份丢弃；接收任务退出后再次清零，避免旧 session.ready 恢复旧身份 |
| 回复开始前失败／取消后仍等待 | 允许匹配本轮、尚未 response.started 的 response_failed 正确退出等待；取消封禁本轮，迟到回复不能重新激活 |
| 准备识别期间说话可能丢首字 | P3 等到 speech.started 和设备显示“正在录音”后才开始上传，尚无准备期预录；当前操作要求等待录音状态，P4.2 再补预录和云握手期间的有界缓存 |
| 正常关闭帧抢在业务事件前处理 | 正常 1000 关闭保留接收 FIFO，让 session.closed 先交给控制器解释，不抢先记故障；未宣布断线仍失败。正常关闭与 r 重连路径有主机回归 |
| 停播只拉低 SD 可能留下旧 DMA 音频 | 停止前先使生产者失效，清播放队列／解码状态并重建 TX DMA；丢弃旧回复迟到数据。主机生命周期检查通过，实际停播延迟与“旧音不复活”仍待实机验收 |
| 异常／取消时清理未覆盖全部路径 | 下行首个控制消息发送失败也释放 Opus encoder；接收异常仍结束 worker、loop probe 和 pipeline；ASR 在 finally 关闭；停止前释放受背压阻塞的回调，并等待任务退出 |
| Opus 前瞻、尾帧和任务栈预算 | 使用 pre-skip／有效结束位置处理首尾，补齐整数帧结束的编码尾包；为固定点 Opus 的栈需求配置接收／上行任务栈及 PSRAM 支持。协议及双向互解检查通过，未据此宣称实机曾栈溢出或音频无截断 |

## 4. 仍未解决的问题及后续方法

### 上行到达停顿与设备写超时

最新配对现场记录：

| epoch／turn | 服务端观察 | 设备观察 |
| --- | --- | --- |
| 3677199172／1 | 到达空档 2531 ms，媒体落后 2460 ms，queue=0 | 约 1263 个 20 ms 帧时失败；最长发送约 223.9 ms，队列升至 11 |
| 1644267682／3 | 本轮到达空档 1406 ms，媒体落后 1341 ms，queue=0，worker=waiting，事件循环最大延迟 25 ms，未记录 ASR 错误 | 约 850 个 20 ms 帧，即 17 秒音频时失败；最长发送约 223.3 ms，队列升至 11 |
| 953293006／11（P4.2自动模式） | 本轮到达空档1391ms、媒体落后1273ms，queue=0，worker=waiting，loop_lag_max=25ms，asr_reason=none | 第40个处理帧附近写失败，最长发送223.69ms、队列11；内部约79KB、alloc_failures=0 |

三次都超过750ms媒体保护阈值。检查发生在入队前，所以queue=0仍可报uplink_backlog。设备transport_poll_write(0)表示等待socket可写到期，非完整发送映射为263／ESP_ERR_TIMEOUT；约223ms的测量与200ms预算及额外开销相容，但不能单独解释完整的约1.4／2.53秒空档。

目前仍不能区分设备采集／调度暂停、Wi-Fi／TCP 停顿或中间缓冲，也不能严格排列设备写失败与服务端拒绝的先后。帧数差不能直接当作 TCP 丢包数。保持程序不变、靠近接入点或更换网络对照；后续补充采集回调最大间隔、设备队列音频年龄、RSSI／断线原因及抓包证据。Wi-Fi 省电已默认关闭；不把单纯扩大队列或延长阈值视为根因修复。

2026-11-10用户要求暂缓此项，先按现有中文交互基线规划P4.3；问题仍为未解决／待定位，不改媒体保护预算。自动模式turn 5–8的正常空识别属于另一条声学／端点线索，不能与turn 11断连合并定因。

### 自动收尾后 60 秒未收到 Pong

epoch=3832586850、turn=4 的设备记录 no PONG received for more than 60 seconds after PING，随后 network_failure。用户确认未按 s，由设备自行结束录音；源码存在约 30 秒自动收尾路径，但该轮完整时序缺少配对服务端日志。

已确认设备未收到 Pong；尚未确认服务端进程／事件循环、网络或设备 WS 处理哪一环停顿。正常异步等待 ASR／LLM／TTS 不应停止服务端接收心跳，不能写成“噪声让 LLM 思考太久导致断线”。需要同一 epoch／turn 的 voice_failure、voice_asr_summary、voice_ws_closed 及循环延迟；此项仍待定位，未通过延长 Pong 时限掩盖。

### 尚未完成的硬件验收

首尾音完整、连续多轮、手动取消和 DMA 实际停播、PCM 回退、长时待机后录音、重连隔离、长回答显示、CPU／栈／内部 RAM／PSRAM／电源稳定性仍须按[P3 验收表](p3_device_acceptance.md)补齐。P4 的 VAD 可改善讲话管理，不是上行网络或 Pong 故障的修复。
