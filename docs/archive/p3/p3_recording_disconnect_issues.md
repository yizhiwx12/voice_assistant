## 1. 现场现象与结论边界

- 用户操作：开始录音后几秒内断开；在断开前手动结束录音，可正常上传并播报回复。
- 用户确认的屏幕提示：**“上行语音发送失败”**。
- 串口反复出现 `Websocket client is not connected`、`conflict found for GPIO[8]` 和 `I2S TX ready`；播放清理屏障耗时约 12.7–12.8 ms。
- 设备录音阶段的最初失败原因、两端上行队列水位、Opus 编码和发送耗时尚未采集，因此尚不能确定是谁先关闭了 WebSocket。

用户提供的代表片段如下；时间为设备日志时间，不等同于完整的录音起止标记：

```text
W (370703) gpio: conflict found for GPIO[8]
I (370715) max98357a: I2S TX ready: 24000 Hz, 16-bit Philips, DOUT=15 BCLK=16 WS=17
I (370715) conversation: Local playback fence and DMA reset: 12724 us
E (375403) websocket_client: Websocket client is not connected
W (375406) gpio: conflict found for GPIO[8]
I (375417) max98357a: I2S TX ready: 24000 Hz, 16-bit Philips, DOUT=15 BCLK=16 WS=17
```

`Websocket client is not connected` 表示组件在尝试发送时已不处于连接状态；屏幕提示来自设备上行任务的失败分支。这两项定位到发送链路失效，但没有记录最初断开原因。GPIO8 的重复占用告警来源已确认；目前没有证据表明它直接导致 WebSocket 断开。

当前没有“录音 5 秒自动断开”的设置：设备单轮录音上限约 30 秒；WebSocket 的 `network_timeout_ms=5000` 是网络操作超时，并非正常录音 5 秒就结束；Ping 为 20 秒、Pong 超时为 60 秒，服务端应用空闲超时为 90 秒。接收队列也有满队列等待 5 秒的保护，但需要持续下行阻塞，目前没有证据支持其为录音阶段的主要触发点。

## 3. P3-001：ASR 节流累计延迟

涉及 [doubao_streaming.py](../../../server/providers/asr/doubao_streaming.py) 的 `_send_audio()`，以及 [voice_websocket.py](../../../server/transport/voice_websocket.py) 的上行 worker 和队列。

修复前每块默认为 100 ms PCM。发送后执行：

```python
self._next_send = loop.time() + len(pcm) / 32000
```

以发送完成时刻重新安排下一块，会把发送和调度开销逐块累加。上行 worker 同步等待 ASR 的 `feed_audio()`；设备持续每 20 ms 产生音频，服务端队列只有 25 项，约 500 ms。积压超过队列容量时，服务端抛出 `Uplink backlog exceeds 500 ms; reconnect`，外层统一返回 `voice_session_failed` 并以 1008 关闭连接。这是一条可以解释“短录音成功、持续录音后断开”的路径，仍需现场数据确认。

### 已执行的无云模拟

使用本机 Windows Python 3.12、生产 provider 的 `feed_audio()` → `_send_audio()`，按绝对时钟每 20 ms 投入 640 字节 PCM，输入队列为 25 项；云端发送完全使用 mock，不连接 ESP32 或云服务。模拟在内存中运行，没有保存成回归测试文件。

| 模拟条件 | 结果 |
| --- | --- |
| mock 发送不增加等待 | 运行 12 秒未溢出，队列峰值 3 帧 |
| 每块 mock 发送加入名义 5 ms 的 `asyncio.sleep` | 首次约 5.016 秒溢出；计时复验约 5.312 秒溢出 |

当前 Python 的单调时钟为 `GetTickCount64()`，报告分辨率为 15.625 ms。计时复验中，名义 5 ms 等待的实际平均耗时约 14.059 ms，100 ms 音频块的发送完成间隔平均约 110.739 ms。**注入的等待不是实际云端耗时，模拟结果不证明现场根因已经确定。**

### 已实施的处理办法

`_AudioPacer` 以首包发送开始时刻为基准，用累计有效 PCM 样本数计算绝对 deadline，发送完成耗时不再叠加到下一包。迟到或输入停顿后，包间隔至少为上一包音频时长的 90%，限制追赶速度；100 ms 块最快每 90 ms 发一次。尾块按实际样本数计时，整块结束仍发送空 EOF；新轮使用新的 provider/pacer，取消后再次检查状态，阻止等待中的旧包发送。

以下约束已落实并纳入回归：

1. 从首块音频建立单调时间基准，按累计有效 PCM 样本数推进后续发送目标，包含非整块尾部，避免每块都把发送完成耗时叠加进去。新一轮必须重置时间基准。
2. 明确首块、尾块、输入暂时停顿和迟到后的发送策略，限制追赶速度，保持云端要求的发送节奏；不要在阻塞恢复后一次性倾倒大量音频。
3. 保留有界队列与停滞失败机制；单纯增大队列或延长超时不能消除长期速度失配。
4. 增加持续至少 30 秒、20 ms 输入的离线回归，覆盖发送延迟和调度抖动，检查队列不会因正常发送开销而持续增长；另测真正慢于实时的连接能明确失败并释放资源，并覆盖尾包、取消及下一轮。绝对时间线只消除节拍漂移，不能保证持续吞吐不足或网络长停顿时仍不断线。

## 4. P3-002：设备持续上行处理能力待测

涉及 [conversation_controller.cpp](../../../main/app/conversation_controller.cpp) 的 `onCapture()` / `uplinkLoop()`、[opus_codec.cpp](../../../main/audio/opus_codec.cpp) 和 [voice_client.cpp](../../../main/network/voice_client.cpp)。

设备每 20 ms 采集 320 个 PCM 样本；上行队列共 27 项，并为控制事件预留空间，音频容量约 500 ms。Opus 编码与网络发送由同一上行任务顺序执行；如果平均处理耗时持续超过 20 ms，本地队列也会逐渐填满，触发“上行积压，请重新连接”并重置会话。单包网络发送的等待参数为 200 ms。当前仅凭“上行语音发送失败”无法判断编码、网络发送、服务器先关闭或清理期间的迟到发送谁先出错。

已实施：采集每帧编码/发送耗时、两者总耗时、数字返回码和上行队列当前值/峰值；记录上行任务栈最低余量、当前堆/内部 RAM/PSRAM 及启动以来最小空闲堆。每 100 帧（约 2 秒）、轮次结束及 `?` 输出聚合指标；正常周期日志由控制任务输出，避免串口打印阻塞编码发送任务。首个故障时另输出快照。

不预先调整 Opus 参数或扩大队列；待设备数据表明存在瓶颈后再优化。需要 PCM/Opus 对照时，应显式建立对应编码的新会话。保留包序和时间线；不采用丢弃部分 Opus 包后继续同一流的做法。

## 5. P3-003：GPIO8 重复占用登记

涉及 [max98357a_audio.hpp](../../../main/audio/max98357a_audio.hpp)、[max98357a_audio.cpp](../../../main/audio/max98357a_audio.cpp) 的 `init()` / `deinit()`，以及 [audio_service.cpp](../../../main/audio/audio_service.cpp) 的 `stopPlayback()`。

GPIO8 仅用于 MAX98357A 的 SD/使能脚；当前显示屏使用 GPIO9–14，麦克风使用 GPIO4/5/6，源码没有另一个外设使用 GPIO8。载板原理图和实物复用情况尚未核实。

每次初始化扬声器都调用 `gpio_config()` 登记 GPIO8 为输出；`deinit()` 会拉低 SD 并销毁 I2S/缓冲，但未释放该引脚的占用登记。下一次停播/DMA 重建再次初始化时，IDF 6.1 检测到已登记引脚并报警，仍继续配置。后面的 `I2S TX ready` 表明初始化成功。约 12.7–12.8 ms 的屏障耗时还包括驱动启动时的 10 ms 延时，与几秒录音阈值不对应。

已实施：`Max98357aAudio::resetPlayback()` 将 SD 生命周期与频繁 I2S/DMA 重建分开。停播时保留 GPIO8 登记并保持低电平，完整删除和重建 I2S/DMA，直到下一次有效播放才使能功放。最终 `deinit()` 拉低 SD、设置下拉、禁用输出，再使用 IDF 6.1 的 `esp_gpio_revoke()` 解除登记，避免 `gpio_reset_pin()` 的上拉暂态。初始化前拒绝占用其他模块已登记的 SD 引脚；失败清理保留可重试的资源状态。

此实现依赖 IDF 6.1 的私有引脚登记 API；升级 IDF 时应重新核对。100 次静音 DMA 重建、启动音与服务所有权交接、14 种注入失败恢复及无 SD 配置的主机回归均通过。实际电平、爆音与停播听感仍需设备复验。

## 6. P3-004：首个故障与观测指标不足

修复前 `ConversationController::fail()` 主要更新屏幕状态，没有把具体原因写入串口；多个任务失败及断连清理还可能覆盖原提示。WebSocket 的 Disconnected/Failure 使用相同阶段提示；服务端又把协议、队列、上游等异常统一为 `voice_session_failed`。因此此前屏幕和串口内容不足以确认第一次失败的来源。

已实施：

- 每个连接保留并打印首个故障的时间、阶段和稳定错误分类，后续清理错误单独记录；使用 epoch/turn/stream 关联两端事件。
- 设备记录编码/发送返回码、发送耗时及上行队列水位；服务端记录输入队列峰值、ASR 调度落后量及失败分类。
- 接收关闭帧时记录可用的数字 close code，区分本地主动停止、服务器关闭和网络失败。
- 日志只使用固定分类、数字状态码和指标，不直接打印厂商错误正文、音频、凭证或带凭证的地址；面向设备的错误响应继续保持脱敏。

设备端首因锁定持续到显式重连，清理后恢复首个屏幕提示；后续错误单独限量记录。服务端同时捕获 ASR 事件读取器先发出的错误，避免仅记录稍后的发送失败。日志范围限定为语音传输模块，不开启 HTTP access log 或厂商调试日志。

定位时查看以下字段：

| 日志/字段 | 解释 |
| --- | --- |
| 设备 `first_failure reason=...` | 首次本地分类、发生时间、数字返回码及 attempt/epoch/turn/stream |
| 设备 `uplink ... queue/queue_peak` | 应用上行队列当前/峰值，含控制项；音频约 500 ms 容量 |
| `encode_avg_us/send_avg_us/frame_avg_us` | 编码、发送、整帧处理均值，另有最大值；整帧预算约 20000 us |
| `stack_free_min/heap_min/internal/psram` | 上行任务栈最低剩余字节、启动以来最小空闲堆及当前内存水位 |
| 设备 `voice_transport ... close_code/socket_errno` | 可用的数字关闭码和网络错误；不打印远端关闭正文 |
| 服务 `voice_failure first=1 ... stage/category` | 服务端首因；当前 `uplink_backlog` 包含队列超限、音频过龄及相对媒体落后，`asr_events_failed` 代表 ASR 读取路径先失败 |
| 服务 `voice_asr_summary ... lag_ms/send_ms/queue_peak` | 本轮 ASR 最大调度落后、最大发送耗时和连接队列峰值 |

## 9. 最新现场证据与第二轮处理

用户提供 `2026-11-09 22:45:52` 的服务日志：`epoch=1929219700 turn=1 stream=1 stage=device_receive category=uplink_backlog queue=25 queue_peak=25 asr_lag_ms=285.0 asr_send_ms=0.0`。该轮服务端有界队列确实已满，约 500 ms 音频积压；设备同轮约 529 秒出现 `send_max_us=224950 frame_max_us=232572 queue=11 send_result=263`。正常阶段整帧平均约 10 ms，不能据此归因于 Opus 长期算力不足。`asr_send_ms=0` 仅统计已完成发送，不能排除当时正在阻塞的发送。

## 10. 2026-11-10：短时突发、长期待机与统计关联

最新上行故障日志为 `epoch=2593080258 turn=6 queue=25 receive_burst=16`，当时 `asr_lag_ms=157`、`loop_lag_max_ms=25`，没有进行中的 ASR socket 发送。设备同轮记录 419 帧、一次发送约 223.5 ms，本地队列升至 11。附件没有第 6 轮的 `trigger=end`，因此现有证据支持故障时正在上行，不能确认其发生于同一轮播报结束后，也不能严格排列设备发送停顿与服务器满队列的先后。

另一段待机日志的当前身份是 `epoch=2908770132 turn=0`，旁边 `frames=46 packets=47` 却来自旧 `epoch=1963970842`。源码确认统计在重连时未清零，故旧帧数不能作为当前仍录音的证据。该现象符合原 90 秒空闲策略，但现场仍需同 epoch 服务端日志才能确认历史关闭原因。

本轮实施：

1. **短暂拥堵与持续积压分开处理。** 队列保持 25 项，暂满时最多等待 100 ms，每次入队主动让消费任务运行。监测 worker 失败并保留原异常，取消待入队任务后不会晚插音频。入队、消费和解码后发现排队年龄或相对媒体落后达到 750 ms 时，中止会话并发送固定 `uplink_backlog`，不丢包后继续。
2. **补齐网络缓冲积压的观测。** 仅检查队列年龄不足：只读模拟中 20 ms 输入、25 ms 消费时，队龄最大约 672 ms，却有约 1737 ms 相对延迟且未触发旧保护。现以本轮首次音频的服务端时间及 sample_offset 为原点，计算“服务端经过时间 − 音频样本经过时间”；各项携带独立基线快照，避免新轮重置污染旧项。该检查不测首帧到达前的固定延迟，不承诺端到端绝对时延；正在等待的云调用仍受独立超时管理。
3. **待机默认保持连接。** 模板与本地业务配置加入 `transport.idle_timeout_seconds=0`，范围为整数 0–86400。正数才启用有限待机；录音、ASR 收尾、回复任务及有限播放保护期间不算待机，忙碌结束后获得完整空闲预算。未发 `playback.done` 的工具使用音频时长加 5 秒的有限保护，到期不虚构播放确认。
4. **正常关闭不再显示服务错误。** 有限待机到期发送带身份的 `session.closed / idle_timeout`，以 1000 正常关闭，日志为 `voice_session_idle`。固件正常清理，按 `r` 重握手后建立新轮，不重放旧问题。未宣布的断线和真实故障仍保留首因、按 `n` 重连。有限待机与本地准备录音恰好交叉时仍保守报 `idle_close_active`；默认长期待机不触发该策略。
5. **修正统计污染。** 新 attempt、session.ready 和新 turn 重置统计；工作任务写入前在同一锁内再次核对输入身份，旧轮 End 的迟到尾部不覆盖新轮统计，也不发布新轮汇总。增加 `active_epoch/active_turn/metrics_current`；RTOS 物理队列仍可能短暂含尚待丢弃的旧 epoch 项。
6. **提供 Wi-Fi 对比配置。** `VOICE_WIFI_POWER_SAVE` 默认关闭，显式使用 `WIFI_PS_NONE`；可开启以与原 MIN_MODEM 对比。当前发送预算 `VOICE_UPLINK_SEND_TIMEOUT_MS` 仍为 200 ms，可选范围 100–500。关闭省电是验证延迟来源的对照措施，不能据此认定路由器或省电是现场根因；100 ms 服务端等待也不保证设备发送低于 200 ms。
7. **修复异常释放边界。** 最初下行流控制帧发送失败或取消时也释放 Opus encoder；接收任务抛异常后仍结束 worker、事件循环探针及 pipeline，避免清理被重复异常打断。

## 12. 2026-11-10：确认响应等待超时并修复

更新诊断后的现场日志 `01:43:42.750 epoch=2150485179 turn=1` 明确记录首因 `stage=asr_feed category=provider_failed asr_reason=receive_timeout asr_upstream_code=0 asr_upstream_close_code=0`。设备收到 `asr_events_failed`，随后服务器以 1008 关闭。服务端收到 1498 帧、队列当前 6/峰值 14、最大排队 266 ms、本轮最大相对媒体落后 254 ms；设备采集 1500 帧、上行队列峰值 1、发送最大 4.607 ms。这里已确认本地 ASR 接收等待到期，没有记录到厂商错误码或云连接关闭码；设备收尾失败是服务端已中止后的后续事件。

根因是旧适配器将“没有识别响应”按单次 30 秒 `receive()` 超时处理。无人声、仅背景噪声时，可以持续发送有效音频却没有中间识别结果；这项计时与设备 30 秒自动提交接近，导致最终结束包尚未处理时先报故障。

已实施：

1. 握手仍需在 `timeout_s` 内获得首个响应，每次发送仍有独立时限，默认均为 30 秒。
2. 录音时根据握手完成时间及最近一次**成功发送非空普通音频包**的时间判断输入进度。持续成功输入可保持同一个待收任务，不要求中间识别结果；空 feed、未凑满块的本地缓冲、远端心跳或仅收到响应不刷新进度。输入真正停滞仍报固定 `input_timeout`。
3. 等待期间只保留一个底层 `receive()`，旧期限到达后重算进度，不重复取消/重启 aiohttp 接收。异常和取消时回收该任务。
4. 开始有序结束后，不再让旧接收期限抢先失败。EOF 发送仍有发送时限；发送成功后，`end_utterance()` 另给最终结果完整 `timeout_s`。生产 pipeline 的 `finally` 保证失败/取消也关闭适配器。
5. 只有云端真实返回空 final，才走已有 `empty_utterance` 流程，设备提示未识别到语音并保留会话。不吞掉云端拒绝、关闭或协议异常，不将缺失最终结果转换为空成功；输入最大时长与队列/媒体延迟预算保持原值。

软件验证：完整离线服务端 **183 项测试通过**，无跳过，耗时 31.399 秒，日志 `build/p3_silent_recording_fix_unittest.log`；针对性 **40 项**通过，日志 `build/p3_silent_recording_targeted_tests.log`；实时配置与原生 Opus 检查通过。新回归覆盖跨多个超时周期持续输入但没有识别响应、底层接收不中途取消、空输入及响应不能掩盖停滞、握手超时、EOF 跨旧期限及完整最终结果预算。真实适配器与真实 pipeline 的长静音及同会话下一轮两项在旧实现中失败，修复后通过；缺失 final 的真实超时回归同样通过，全程使用 mock 上游。

本次只改服务端适配器、测试和文档，未修改用户配置、密钥或固件，未调用云 API，也未重启正在运行的服务。实机需退出旧服务并重新启动，固件不必重烧；分别复测风扇背景声至 30 秒自动提交、持续说话至自动提交、手动提前提交，以及空识别后直接开始下一轮。若云端返回空最终结果，预期提示“未识别到语音，请重试”且会话保持；背景声是否被识别为文字仍取决于云端，当前没有本地 VAD。P3 继续等待实机复验，不能将离线通过等同于云端或设备验收完成。

### 自动收尾后的心跳超时
