## 2. 测试环境与始终保留的约束

设备为 ESP32-S3 N16R8，ESP-IDF 6.1，ESP-SR 2.6.1，模型 `vadnet1_medium`。麦克风 ICS-43434 使用 I2S1，GPIO4/5/6；MAX98357A 使用 I2S0，GPIO15/16/17，SD 为 GPIO8。此次 AEC 修复没有更换引脚、云端服务或模型。

默认 `build/` 关闭 AEC，使用 `M` 单麦路径；独立 `build/aec-test/` 开启 AEC，使用 PCM16／16 kHz 的 `MR` 交错输入 `[mic0, ref0, mic1, ref1, ...]`，AEC 为 `SR_LOW_COST`，NS／AGC／WakeNet及自动插话仍关闭。手动 `r/s` 保留原始 PCM 基线，自动 `a` 路径使用 AFE 输出。

固定保护没有为“消除报错”而放宽：AFE 入口 8×20 ms，待配对麦克风 10×20 ms，参考等待约 80 ms，配对年龄上限 200 ms；TX DMA 4×240 样本／24 kHz，约 40 ms。未知参考仍明确失效，不补零冒充有效参考，不丢旧 PCM 追赶，不扩大队列或关闭看门狗。

接口约定也按锁定库核实：一麦 `afe_feed()` 返回处理后单声道环的字节数，即每通道 `count×2`，不因为 MR 输入双通道就再翻倍；fetch 返回的 SDK PCM 必须先完成统计、复制与回调处理，再进行新增的预算等待。这是当前实现的接口与所有权约束，不另记为日志已证实的硬件故障。

只有证明确为静音的数字区间才能提供零参考。播放参考来自设备解码、音量处理后的实际 DMA 内容，不能使用服务端编码前的音频替代。DMA 完成不是扬声器实际出声的传感器反馈。

## 4. 部署时出现的两个操作问题

### 4.1 PowerShell 把两条命令粘成一条

用户曾输入 `cd C:\esp-project\voice_assistantidf.py -B ... -p COM7 ...`，`idf.py` 被粘在目录后，PowerShell 将 `-p` 交给 `Set-Location`，报参数有二义性。这发生在烧录之前，与 AEC 算法和编译结果无关。

处理是在已初始化 ESP-IDF 的终端逐行执行，按回车分开：

```powershell
cd C:\esp-project\voice_assistant
idf.py -B build/aec-test -p COM7 -b 115200 flash monitor
```

### 4.2 COM7 打开失败／拒绝访问

当时构建与应用分区检查已经通过，失败发生在 esptool 打开 COM7，提示 `PermissionError(13)` 和 `port is busy or doesn't exist`。这不是 AEC 编译失败。

处理是退出旧 IDF monitor、VS Code 串口监视器或其他串口工具，核对实际端口，必要时重新插入设备再核对端口后重试；串口只由一个程序持有。`115200` 是此次采用的保守烧录速率。不能仅凭该提示断言哪个程序占用，也无需因此擦除 Flash 或修改 AEC 代码。

## 5. 第一批：启动即失效与播放切换缺口

**现象与证据。** 初始固件三份启动日志在约 5.1–5.3 秒出现 `capture_timeline`，有两份 RX overflow6／丢1536样本／pairs0。另两份启动正常，却在首次播放重建 TX 后约108／111 ms出现 `reference_gap`，目标仅60/320或206/320样本有效，RX 无溢出。

**问题一：消费者尚未就绪，RX 已开始运行。** 原流程先启用麦克风，后初始化 AFE、模型和任务；有限 DMA 队列可在真正读取之前积压。修复为先配置但保持 RX disabled，全部消费者就绪后由采集任务启用并立即 read；启用和首次读取之间不再插入 UART、分配或模型初始化，失败握手与清理同时覆盖。

**问题二：健康 AEC 的播放切换破坏了连续数字参考。** 每次播报／取消重建 TX 并切换 serial，会带来新的物理 generation、FIR 预热和 SD 边界未知区间。修复为健康 AEC 清软件队列、5×10 ms 零块有界 drain 后静音，下一轮沿用物理 generation；serial 只区分播放作用域，不再重置连续 FIR。只有原始左右 DMA 都为零且一致，才承认跨 SD 边界是有效静音。排空失败仍停 AEC 并执行硬件保护，默认非 AEC 的重建栅栏保留。

**验证与后续。** 主机覆盖初始化顺序、失败清理、跨 serial 连续非零 PCM、空回复取消、未知缺口；两配置构建通过。新版首次 read 调用延迟83–91 µs，证明调用顺序改善，但仍在启用后144–160 ms溢出；另一次转为配对超龄。由此明确“调用了 read”并不证明“read 及时返回并持续消费”。健康 AEC drain 保留最多约50 ms已提交DMA尾音的设计边界，不能由软件计时直接推断主观停声延迟。

来源：[启动与播放切换记录](p43c_startup_and_playback_fixes.md)。

## 6. 第二批：目标参考已完整，仍被最新尾部阻挡

**代码缺陷。** 旧 `reference_history_pending_` 代表最新 TX 尾部尚待转换，却被用于阻止所有麦克风配对；即使旧目标的320个参考样本已完整，也必须等待。连续播放持续产生新尾部，这种全局阻断可能使旧目标超过200 ms。

**修复。** 先检查目标本身：完整则按序交接；不完整且历史仍 pending 才等待；追完历史仍缺数据才报 `reference_gap`。已知静音按可证有效区间消费，不用零填未知区间。新增“目标完整、较新尾部仍 pending”的回归，原实现失败、修复后通过。

**诊断补齐。** 保存首次 read 调用与完成、返回样本范围、耗时和读间隔、当前 phase／实际核心、raw 回调耗时。首次 RX overflow 在 ISR 一次性冻结消费者进度，发生发布冲突只标记 incoherent，不等待或打印；详细首因由非采集路径、播放锁外延后输出。AEC 首错同时冻结最老目标、年龄、覆盖和 pending，不被次生错误覆盖。

**后续实机。** 两次实际消费者在 CPU0，`phase=read` 已持续约95.6 ms时溢出；read 最终耗时158／173 ms，之前 raw 回调只有73／86 µs。这排除了“尚未调用 read”和“raw 回调很慢”两种解释，但没有调度跟踪，不能将 Wi-Fi 关联重试定为唯一原因。另一次 pair_age208 ms需继续检查参考服务。

来源：[配对与连续采集诊断](p43c_pairing_and_capture_diagnostics.md)。

## 7. 第三批：明确采集核心，给必要参考处理机会

**证据。** RX 待处理队列约80 ms，短时未及时服务就可能溢出。任务源码未绑核也不保证一直可迁移；锁定构建中浮点／协处理器调用链可能将任务固定到当前核心，因此运行时核心必须记录。

**修复。** 仅 AEC 显式安排 CPU1：capture7、play/reference6、AFE feed/fetch5。停止 AEC 路径重复运行 B 的声学81候选搜索及不会被消费的诊断采集队列；AEC 用实际配对覆盖验证，不再以 probe attempts 是否增加判定正常。阻塞 TX 写前提供最多4次／软16 ms参考追赶机会，单次仍8块／软4 ms，并逐步检查取消、serial和运行状态。该预算是服务边界，不承诺单次不可抢占运算的硬实时上限。

**验证与后续。** 动态主机时钟同时生产 TX10 ms、RX16 ms、麦克风20 ms，注入70 ms阻塞写；去掉追赶的临时负例失败，修复通过。真实设备首因转为 `frontend_backlog`：RX健康、目标参考320/320、pending0，但 AFE 项目入口8/8。说明采集／参考路径改善，AFE 调度成为下一瓶颈。

来源：[音频任务调度修复](p43c_audio_scheduling_fix.md)。

## 8. 第四批：AFE 优先级不公平，首因被迟到快照掩盖

**调度缺陷。** 同核 play/reference6 持续就绪时，AFE5 是严格较低优先级；单独 `taskYIELD()` 只让同级就绪任务轮转，不能保证低优先级 AFE 获得处理时间。两份实际日志在32.369／116.191秒先报 AFE 入口满，之前目标参考完整，不能再归因为 RX 溢出。

**修复。** AEC feed/fetch 提升为6，与参考共享时间片，capture保持7。冻结 `LocalAudioFrontend::FailureSnapshot` 时先保存错误、时间、队列与feed/output计数，再输出 UART；详细日志延后，保留真正 `ESP_ERR_TIMEOUT`，不把所有失败改写成 `ESP_FAIL`。

**诊断边界。** 旧 `?` 在首错7–11秒后，feed184／240 ms最大值可能含失败后的在途工作、等待和抢占，不能当作首错瞬间的纯DSP耗时。新快照也只是若干原子计数，不是完整 RTOS 调度轨迹。

**后续实机。** 第四批约30.7秒首错是 pair_age204 ms：AFE queue0／peak2，feed/output均408064，RX健康，参考待转换19个10 ms块。入口已经不是首因，转而定位必要参考吞吐。失败尝试没有重新 query，189/320是上次查询，不能把它写成失败时的新覆盖结果。

来源：[AFE 同级调度与首因快照](p43c_frontend_fairness_fix.md)。

## 9. 第五批：参考转换与时间映射的实时吞吐不足

**证据。** 上述 pending19 与配对204 ms超龄说明参考服务落后；此时 AFE 入口不满。有效映射范围包络覆盖目标末端，不代表中间每个样本都有效，不能通过跳过逐点检查“修复”超龄。

**修复。** append时缓存映射边界，减少查询时对无关块重复进行 double／ceil／floor／距离计算；引入轻量 `HealthRange`；四个参考生产源局部采用 `-O2 -ffp-contract=off`。保持191抽头 FIR、连续相位、约1.979 ms群延迟和IEEE语义，不启用 fast-math，不放宽200 ms保护。

**验证与后续。** 35,499个PCM样本 oracle、四组优化前后差分轨迹的覆盖mask／包络／PCM哈希一致，monitor及AudioService回归、双构建通过。实机第五批转为30.908秒入口8/8：参考320/320、年龄100 ms、RX健康。此时不是原参考超龄，而是暂时交接背压被直接判为永久故障。

来源：[参考吞吐优化](p43c_reference_throughput_fix.md)。

## 10. 第六批：暂时队满不应立即永久停用前端

**交接缺陷。** 原实现先从配对队列移除头帧，再零等待送 AFE；只要 AFE 入口暂满，就不可恢复地停止。瞬间背压与持续吞吐失控没有分开，且存在已移除头帧的所有权问题。

**修复。** 新增 `tryEnqueuePaired()`，暂满返回 `ESP_ERR_NOT_FINISHED`，保留同一队首、样本和顺序，后续服务机会再试；成功后才移除。持续拥塞仍受原200 ms年龄及固定容量约束，不丢最旧音频、不重复交接。PSRAM 栈水位扫描降为每50块一次，减少热路径开销。

**小智参考的使用方式。** 对照官方固定提交 `a73e9a7e266e3196d1368ba46c30bee0d81f0a64`，参考采集、前端、网络分离和有界交接。没有照搬上传边界丢旧帧、Box Lite同率共时钟缓存、补零、FD/NLP配置或优先级数字。本项目独立16 kHz RX与24 kHz TX需做软件时线映射，不能直接套用另一种硬件架构。

**验证与后续。** Frontend M26／MR29；20次重试恢复后5120个双通道样本一致；AudioService FIFO和非零PCM保持；3200样本年龄允许、3201拒绝仍通过。随后第六批设备出现 WDT／时线失效时入口queue0／peak2、frontend_waits0，说明该次不是入口满；暂满恢复路径在主机已验证，不能冒称实机已触发验证。

来源：[小智对照与交接背压修复](p43c_xiaozhi_backpressure_fix.md)。

## 11. 第七批：时钟抖动误判与下行任务持续就绪

**两类证据分开。** 第六批47.698／85.197秒有 CPU1 `IDLE1` WDT，回溯包含 `VoiceClient::dispatch → onBinary → feedPlayback → Opus decode`；85.366秒首个 reference_gap，时间线healthy0，但RX健康、AFE入口未满、pending0、配对年龄120 ms。WDT 与时间线失效相邻，不足以证明唯一因果关系；任务名快照也不等于回溯始终属于同一个任务。

**时钟模型修复。** ISR时间是回调执行时刻，旧约1秒窗口只要一次超出±2000 ppm就永久失败。独立重现表明单次3 ms ISR延迟即可误触发。保留频偏阈值，异常窗口不更新模型，连续两个独立窗口同方向超限才确认；正常窗口清嫌疑、反向重新记。50 ms突跳、非单调、overflow／invalid等保护不放宽。

**调度修复。** AEC下行 `voice_rx` 移CPU0／优先级5，内部栈fallback同样绑定；默认非AEC不绑核。两配置累计8 ms墙钟或8消息后，回调返回、消息释放且锁外 `vTaskDelay(1)`，FIFO与反压保留。新增首个时钟失败不可变快照，记录来源、原因、残差、ppm、窗口和bad_windows；没有时钟首因时保持valid0，不被后来的错误回填。

**验证边界。** 健康与频偏轨迹、传输生命周期、控制器、AudioService及双构建通过。指定微秒抖动轨迹中±2500／3000／5000 ppm约两秒被拒绝，但混合毫秒延迟轨迹最慢约37秒才被其他映射保护拒绝；不能将“两秒”写成所有组合的检测上界。

**后续实机。** 新附件含core0接收与新时钟诊断，参考healthy1／clock_errors0、AFE正常，却仍五次CPU1 WDT并有播报卡顿。附件无启动ELF，因此只确认新诊断已出现，不能断言完整核对第七构建身份。该次已经不是前端永久失效或时线缺口，应转查播放供给及整体调度。

来源：[时钟确认与下行调度修复](p43c_clock_scheduling_fix.md)。

## 12. 第八批：前端健康，仍有 CPU1 看门狗和播报卡顿

**现象。** 附件 `e763064a-6d49-48e1-8be3-623fd9538ab9` 在39.391／65.083／120.972／163.564／189.318秒出现五次IDLE1 WDT。回溯涉及fetch统计、AEC FFT、队列及LVGL；同时 AEC active1／error0、时线healthy1／clock_errors0、RX无溢出、alloc_failures0。可以确认CPU1空闲任务未及时运行，不能据不同瞬间的任务名断言某一个任务独占五秒。

**修复方案。**

1. AEC feed保持CPU1／6，fetch及VAD输出移CPU0／6，capture仍CPU1／7、play/reference仍CPU1／6。默认M调度保持原策略。
2. AEC feed/fetch累计8 ms保守处理墙钟或4次尝试后，完整PCM统计、复制和输出回调结束再真实等待1 tick；覆盖快速空返回及停止时排空，不在持有SDK借用PCM时让出其所有权。
3. 每20 ms播放帧常态重参考服务由5次减为2次；10 ms写片之间只轻量pump，已有目标等待时仍保留写前有序catch-up。保证必要参考前进，也减少补TX前的重复重运算。
4. AEC播放累计8 ms或2帧，在完整帧、回调结束且锁外等待1 tick；不在两个10 ms写片之间增加等待，取消、停止和错误及时退出。
5. 增加 `schedule`、`playback_flow`、`playback_service`，分开观察解码、入队等待、活跃期队列暂空、写耗时、写结束至下次开始的间隔和预算等待，按播放作用域重置。

**验证。** 五个主机runner通过：Frontend M26／MR35、AudioService M/MR、控制器30场景、参考时间线、clock-jitter；默认与独立AEC两个真实构建通过，并核对编译对象、链接、产物hash和配置。固件未通过扩大DMA、放宽保护或调高看门狗超时掩盖问题。

**最新设备结果。** 已由本轮附件确认运行新版本，见下一节。此前每次断音没有对应的物理DMA追踪或服务端同步证据，不能反推所有历史卡顿都只由这一原因造成；本轮正常反馈支持这组修复在当前场景有效。

来源：[播报供给与前端协作修复](p43c_playback_stutter_fix.md)。

## 14. 现场容易混淆的问题与正确判断

| 提示／指标 | 应如何理解 | 不应直接推断 |
| --- | --- | --- |
| `microphone_unavailable`、本地检测异常 | 常是参考／采集首因后主动停AFE的次生提示；回看更早首错 | 麦克风一定损坏，或与上次原因完全相同 |
| `capture_timeline`／RX overflow | 采集连续性已经丢失，应停止依赖它的AEC | 网络断开或PSRAM耗尽 |
| `reference_gap` | 目标参考未知、不完整或时线已失效；结合第一原因及覆盖mask | 一定是GPIO8冲突，或应该用零填满 |
| `pair_age` | 最老配对目标超过200 ms，查pending、覆盖、AFE背压与服务进度 | 一定是云ASR或Wi-Fi问题 |
| `frontend_backlog` | 项目AFE入口交接受阻；区分瞬间背压和持续超龄 | ESP-SR内部50帧环一定满，或必须增大所有队列 |
| `frontend_waits>0` | 第六批后的暂满重试次数，要看队列能否回落、输出能否前进 | 故障次数 |
| `Ringbuffer of AFE is empty` | 该次fetch没有足量输出；结合后续进展和输出停滞保护 | 单条警告已证明前端停止或SDK忙等 |
| `IDLE1` WDT | CPU1空闲任务未及时运行，需看完整调度与回溯 | 任务名快照里的任务独占了整个超时窗口 |
| feed/fetch／解码／参考服务耗时 | 墙钟可能包含等待和抢占，独立最大值分别解释 | 纯DSP耗时、CPU占比，或几个最大值可以相加 |
| `silence`／零PCM／成功I2S写 | 包含源零、drain、SD边界；成功写是字节接受 | 物理DMA欠载次数、扬声器确实发声或ERLE |
| probe attempts0／`calibrated=0` | 当前AEC停止重复声学搜索，尚未自动声学校准 | AEC一定未运行；应同时看active、pairs、feed/output |

**拔掉扬声器是否影响 AEC？** 数字参考取自TX PCM／DMA，单纯扬声器不响不会让这个数字链路自动出现 `reference_gap`。没有实际扬声器回声时，AEC也就没有对应声学回声可消除，不能用该条件评价真实回声抑制效果。若拔插涉及功放供电、信号或共地，则可能另有电气变化，应按实际接线与日志单独判断；本轮未把“拔了音响”当作已确认故障原因。

**为什么 Flash／PSRAM 很多仍可能失败？** N16R8的16 MB是Flash，8 MB是PSRAM，不能直接变成内部／DMA RAM。早期P4有内部RAM不足导致WebSocket任务创建失败，已另做LVGL迁移和内存分配布局修复；本次AEC批次多份日志分配失败0，不能继续用旧内存故障解释全部新错误。详见[P4问题汇总](p4_issue_summary.md)及[内存记录](p4_memory_budget.md)。

**风扇、弱音和网络旧问题。** 风扇关闭后识别恢复、弱音漏字、英文效果和上行到达停顿属于此前独立记录。本次不改增益、ASR模型、网络超时或队列；不能把所有空识别和短断连重命名为AEC问题。详见[P4问题汇总](p4_issue_summary.md)及[P3问题汇总](../p3/p3_issue_summary.md)。
