## 现场现象与首因

## 前端、参考和资源证据

四个前端快照均为 `ready=1 aec_requested=1 aec_active=1 error=0`；最终输出 4,272,640 samples／13,352 frames，输入与输出样本计数相等。这些是故障后仍健康的采样，不是每次锁争用瞬间的同步线程追踪。

末次数字参考／采集快照为：

- `reference_alignment healthy=1 mapped=26724 unmapped=0 clock_errors=0`，最大时钟残差 96 µs。
- `capture_timeline valid=1 overflow=0 invalid=0`；重采样 `errors=0 gaps=0 overwritten=0`。
- `aec_pairing active=1 error=0 pairs=13374 last_reference_valid=320`，前端等待 0，队列历史峰值 8。
- 内部可用内存从首次手动快照 59,471 bytes 到末次 59,251 bytes；末次 PSRAM 可用 7,458,020 bytes，分配失败 0。采集／播放最低剩余栈 1,792／940 bytes。该样本不证明长期资源安全，也没有栈溢出的证据。

日志没有 E 级记录、`first_failure`、`aec_reference_failed` 或 `AFE/VAD unavailable`，但明确发生了 D1 观察失效，不能据此记“一切通过”。保留 62 次 AFE empty 警告、1 次 WakeNet 未加载提示，以及初连 Wi-Fi reason 201 的一次重试；连接后同一 epoch 完成四轮，没有这次问题对应的 WebSocket 首次故障。WakeNet 配置原本关闭。AFE empty 提示本身也不等于前端永久失效或播报卡顿。

## 原代码为什么会关闭观察

初版 D1 为了避免 AFE 回调等待控制器，使用 `state_mutex_` 的非阻塞 `try_lock` 核对回复身份。这一方向保留了音频线程的响应性，但实现把“某一瞬间锁正被其他任务占用”直接转成 `controller_busy`，清候选并永久停用本项观察。

正常接收文字／音频、更新回复状态也会短暂持有同一把锁。一次 `try_lock` 失败并不能证明 AEC、参考或身份失效。因此这三次“不可用”的直接原因是控制器保护策略过严。附件没有记录持锁任务、持锁时长或与扬声器声音的同步关系，不能进一步声称回声造成了锁争用，或已经测得回声消除不足。

## 本批软件修复边界

修复使用独立的 32 位原子回复修订栅栏隔离旧身份；AFE 回调不再尝试获取 `state_mutex_`，并在加入候选 PCM 前后核对修订号。普通文字／音频更新占用状态锁时，连续的前端 PCM 仍能进入当前候选缓存。活动观察的控制检查也不获取该锁；只有尚未绑定回复时使用非阻塞核对，锁忙则推迟启用，不因普通争用永久关闭观察。

回复封存／代次变化、取消、重连和真实失效仍须使旧候选失效；不能为了避免 `controller_busy` 而让旧回复音频混进新候选，也不能静默丢一帧后继续累计“连续人声”。AEC 故障、采样不连续、缓存溢出和真实前端无进展保护继续保留。D1 仍只观察，不开启 D2 自动停播、回复取消或新轮上传。

本批不调整 AEC 算法、音量、增益、模型、参考时线或网络预算，不用堵住扬声器作为使用条件。除控制器 `.cpp/.hpp` 外，现有 `main/` 源码均与修复前基线一致；配置、模型、分区和 bootloader 二进制也保持一致。完整软件结果见修复软件报告（历史生成产物：`build/p43d1_busy_verification.json`，当前目录未保留）。初版 `build/p43d1_verification.json` 和本次设备观测报告保留原时点事实，不覆盖为“修复已在设备通过”。

日志新增 `reply_revision` 与 `boundary_resets`，用于关联回复切换与候选清理。如果边界恰好与加入 PCM 同时发生，累计确认计数可能包含一次随后已丢弃的旧事件；它不代表新候选可继续使用，也不是声学确认或真实插话成功的证据。独立的 500 ms 前端无进展保护仍然有效，不能靠状态锁忙绕过。
