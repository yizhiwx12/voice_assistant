## 这次证据说明了什么

配对附件：设备 `03bb9fd5-f00b-44d2-8208-741b6ffa181f`，服务端 `230d5efc-ec68-47f9-a5c7-e8e77f468c38`。两端时钟不同，只比较各自阶段耗时与相同数字身份，不直接相减本地时间。

| 旧回复身份 | 服务端取消路径 | 设备本地停播返回 | 设备结果 |
| --- | --- | --- | --- |
| epoch `3090991631` turn 1 generation 1 | 17:02:55.941 收到、清理完成、ACK 写出；idempotent，耗时约 0 ms | 确认后 58.1 ms，调用耗时 51.2 ms | 未记录匹配 ACK，确认约 2.012 秒后主动断开 |
| epoch `2165675190` turn 1 generation 1 | 17:03:59.343～344 收到、清理完成、ACK 写出；active，约 0～1 ms | 确认后 65.0 ms，调用耗时 60.9 ms | 未记录匹配 ACK，确认约 2.013 秒后主动断开 |

这两次不支持“云端清理太慢”的解释。`ack_sent` 只表示服务端 WebSocket 写调用完成，不能证明 ACK 已到设备。原设备只在精确匹配时记录 `cancel_ack`，因此也不能仅凭缺少该日志区分尚未接收、分发迟到与身份不匹配。

服务端原 `send_audio()` 对合成得到的每个 20 ms 帧直接发送，没有发送节奏限制。可写的 TCP socket 能容纳很多旧音频；取消 ACK 无法越过已写入的旧字节。两次连接累计分发音频为 989／759 包，当前播放流解码为 508／262 包；各连接只有这一轮回复，差额约 481／497 包，符合封轮后继续丢弃旧包的路径。差额不能直接证明全部是在取消之后接收，也不能把 9.6／9.9 秒媒体时长等同于网络延迟，但与旧音频抢在 ACK 前面进入 TCP 的风险一致。

`queue_peak=16` 是连接累计峰值，不能当作超时瞬间的队列深度。现有日志未观测到 ACK 完整接收边界，所以本批修正已确认的无节奏发送设计，并补齐定位证据，尚不宣称找到了两次失败的唯一原因。

## 本批修改

1. 下行每个 20 ms 帧发送前经过令牌桶，最多允许 200 ms（10 帧）突发，此后按媒体速率补充额度。生产者或 socket 长暂停最多恢复一个桶，不能积攒数秒追赶额度。PCM 与 Opus 包、序号、pre-skip、有效结束样本不变。
2. 节奏等待在 WebSocket 发送锁外执行；取消会中止等待，清理完成后仍由原路径发送 ACK。等待结束重新检查回复身份，旧流不能继续发尾包。令牌桶限制服务端发送突发，**不是设备实际播放前瞻或网络延迟的硬上限**；网络和解码持续变慢仍可能积压。
3. 设备只对目标取消确认增加 `cancel_ack_transport phase=received/enqueued/dequeued` 数字日志，记录完整收包时刻、入队等待、分发累计延迟与即时队列深度。目标文本经过真实 JSON 类型及整数身份校验，非法身份显示 `valid=0`；不输出正文、识别内容或凭证。诊断只覆盖不超过 512 bytes 的此类确认，协议处理上限仍沿用原值，队列 FIFO 不变。
4. 控制器对每个有效身份的 ACK 记录 `barge_in_handoff event=cancel_ack_dispatch`，包含 `pending`、`match` 与目标身份，随后仍只允许精确匹配 ACK 解除屏障。大于 `INT32_MAX` 的 epoch 与 `UINT32_MAX` 已覆盖。
5. 对未上报 `playback.done` 的兼容客户端，按每个成功发送帧更新预计播放结束时间，再加原有 5 秒宽限；不在发送结束后重复等待整段音频时长。生产者或 socket 停顿后重新估算剩余播放。

没有延长设备 2 秒共享预算，没有放宽 750 ms 上行媒体保护，没有改变 AEC、模型、增益或接线。

原有 120 秒回复总预算现在包含接近实际播报时长的下行发送，超过约两分钟的长回复可能触及它；本批未扩大该预算。200 ms 发送预缓冲对实际播报连续性的影响仍需本轮设备观察。

## 上行故障单独记录

epoch `3416088149` turn 1 首错为服务端 `device_receive/uplink_backlog`：接收空档 1344 ms、媒体落后 1316 ms，队列为 0、入队等待为 0、事件循环约 10 ms／峰值 25 ms，ASR 没有上游错误。可确认音频到达过晚；网络波动与设备发送调度停顿均待区分，不能说已证实 Wi-Fi 故障。设备随后写读错误／`uplink_end` 失败属于这次终止过程。附件开头另有两次连接建立超时，尚未建立 epoch，没有发送音频，与取消确认超时分开记录。

本地 `ready=1 aec_active=1 error=0`、参考 gaps 0、对齐 healthy 1、分配失败 0，支持本次没有重现旧 AEC 失效；失败后“不可用”来自会话失败闭锁。
